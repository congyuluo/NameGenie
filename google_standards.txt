Google Java Style Guide Identifier Naming Guidelines

Rules common to all identifiers
- Naming Convention:
  - Identifiers use only ASCII letters and digits, and in a small number of cases noted below, underscores.
  - Each valid identifier name is matched by the regular expression \w+ .
- Guidelines:
  - Special prefixes or suffixes are not used.
    - Not Google Style: name_, mName, s_name, kName.

Packages / Modules
- Naming Convention:
  - Use only lowercase letters and digits (no underscores).
  - Consecutive words are concatenated together.
- Examples:
  - com.example.deepspace (not com.example.deepSpace or com.example.deep_space)

Classes (and Interfaces / Annotations / Tests)
- Naming Convention:
  - Class names are written in UpperCamelCase.
- Guidelines:
  - Class names are typically nouns or noun phrases (e.g., Character, ImmutableList).
  - Interface names may be nouns or noun phrases (e.g., List), but may sometimes be adjectives or adjective phrases instead (e.g., Readable).
  - There are no specific rules or even well-established conventions for naming annotation types.
  - Test classes:
    - A test class name ends with Test (e.g., HashIntegrationTest).
    - If it covers a single class, its name is the name of that class plus Test (e.g., HashImplTest).

Methods
- Naming Convention:
  - Method names are written in lowerCamelCase.
- Guidelines:
  - Method names are typically verbs or verb phrases (e.g., sendMessage, stop).
  - JUnit test method names:
    - Underscores may appear to separate logical components of the name.
    - Each component is written in lowerCamelCase (e.g., transferMoney_deductsFromSource).
    - There is no One Correct Way to name test methods.

Constants
- Naming Convention:
  - Constant names use UPPER_SNAKE_CASE: all uppercase letters, with each word separated from the next by a single underscore.
- Definition (what counts as a constant):
  - Constants are static final fields whose contents are deeply immutable and whose methods have no detectable side effects.
  - Examples include primitives, strings, immutable value classes, and anything set to null.
  - If any of the instance's observable state can change, it is not a constant.
  - Merely intending to never mutate the object is not enough.
- Examples:
  - Constants:
    - static final int NUMBER = 5;
    - static final ImmutableList<String> NAMES = ImmutableList.of("Ed", "Ann");
    - static final Map<String, Integer> AGES = ImmutableMap.of("Ed", 35, "Ann", 32);
    - static final Joiner COMMA_JOINER = Joiner.on(','); // because Joiner is immutable
    - static final SomeMutableType[] EMPTY_ARRAY = {};
  - Not constants:
    - static String nonFinal = "non-final";
    - final String nonStatic = "non-static";
    - static final Set<String> mutableCollection = new HashSet<String>();
    - static final ImmutableSet<SomeMutableType> mutableElements = ImmutableSet.of(mutable);
    - static final ImmutableMap<String, SomeMutableType> mutableValues =
          ImmutableMap.of("Ed", mutableInstance, "Ann", mutableInstance2);
    - static final Logger logger = Logger.getLogger(MyClass.getName());
    - static final String[] nonEmptyArray = {"these", "can", "change"};
- Additional guideline:
  - Constant names are typically nouns or noun phrases.

Non-constant Fields
- Naming Convention:
  - Non-constant field names (static or otherwise) are written in lowerCamelCase.
- Guidelines:
  - These names are typically nouns or noun phrases (e.g., computedValues, index).

Parameters
- Naming Convention:
  - Parameter names are written in lowerCamelCase.
- Guidelines:
  - One-character parameter names in public methods should be avoided.

Local Variables
- Naming Convention:
  - Local variable names are written in lowerCamelCase.
- Guidelines:
  - Even when final and immutable, local variables are not considered to be constants, and should not be styled as constants.

Type Variables
- Naming Convention:
  - Each type variable is named in one of two styles:
    1) A single capital letter, optionally followed by a single numeral (e.g., E, T, X, T2).
    2) A name in the form used for classes (UpperCamelCase), followed by the capital letter T (e.g., RequestT, FooBarT).

Camel case: defined (Google’s scheme)
- To convert a phrase into camel case:
  1) Convert the phrase to plain ASCII and remove any apostrophes.
     - Example: "Müller's algorithm" -> "Muellers algorithm"
  2) Divide into words by splitting on spaces and remaining punctuation (typically hyphens).
  3) Recommended: if any word already has a conventional camel-case appearance in common usage, split it into constituent parts
     (e.g., "AdWords" -> "ad words"). Note: "iOS" is not really in camel case; this recommendation does not apply.
  4) Lowercase everything (including acronyms), then uppercase only the first character of:
     - each word, to yield UpperCamelCase, or
     - each word except the first, to yield lowerCamelCase
  5) Join all words into a single identifier. The casing of the original words is almost entirely disregarded.
  6) In very rare circumstances (e.g., multipart version numbers), underscores may be needed to separate adjacent numbers.

- Examples (Prose -> Correct / Incorrect):
  - "XML HTTP request" -> XmlHttpRequest / XMLHTTPRequest
  - "new customer ID" -> newCustomerId / newCustomerID
  - "inner stopwatch" -> innerStopwatch / innerStopWatch
  - "supports IPv6 on iOS?" -> supportsIpv6OnIos / supportsIPv6OnIOS
  - "YouTube importer" -> YouTubeImporter / YoutubeImporter*  (*Acceptable, but not recommended.)
  - "Turn on 2SV" -> turnOn2sv / turnOn2Sv
  - "Guava 33.4.6" -> guava33_4_6 / guava3346

- Note:
  - Some words are ambiguously hyphenated in English (e.g., "nonempty" vs "non-empty"), so both checkNonempty and checkNonEmpty are correct.
